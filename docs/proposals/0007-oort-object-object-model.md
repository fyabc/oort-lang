# OP 0007: `oort-object` 动态对象模型

- **状态**：Proposed
- **作者**：Oort 设计讨论
- **相关**：[OP 0001](0001-feature-layers-and-dialects.md)、
  [OP 0005](0005-type-system.md)、[设计 04](../design/04-class-object-model.md)、
  [规范：类](../spec/05-classes.md)

## 摘要

定义 `oort-object` 方言的对象模型：实例是**开放的字段袋**，类只承载方法与类方法；
不引入槽（slot）；类体中的 `var` / `val` 被显式拒绝；实例字段优先于类 MRO 查找，
但禁止用实例字段遮蔽类方法；缺失字段读取报错；默认相等与哈希使用对象身份。

槽、固定布局、确定赋值与 `val` 只读属于 `oort-core` 的静态对象模型，
不在本提案范围内。

## 动机

当前实现混合了两种对象模型：

- 实例通过 `this.x = ...` 动态添加字段（Bag），运行时按“实例字段 → 类 MRO”查找；
- 类体中的 `var` / `val` 会作为类作用域的局部变量执行，既不是类属性也不是实例字段，
  语义含混；
- [设计 04](../design/04-class-object-model.md) 的 Slot-Bag-Handler 模型是为
  固定布局与 getter/setter 准备的，直接放进动态方言会产生“共享可变类属性”
  或半静态字段等歧义。

`oort-object` 的定位是动态脚本、DSL 与原型开发，需要的是简单、可预测的开放对象。
因此先把动态对象模型单独定清楚，把槽留给静态方言。

## 设计

### 1. 实例：开放字段袋

- 实例创建时字段袋为空，没有固定布局，也没有“未初始化字段”概念。
- `this.x = value` 在字段袋中添加或更新字段；字段可以在任何方法中创建。
- 读取不存在的字段抛出 `OortAttributeError`。
- 字段只保存值；本提案不引入 getter/setter、Handler 或属性描述符。
- 裸名字（`x`）永远不表示字段；访问字段必须写 `this.x`。

### 2. 类：只承载方法

- 实例方法存放在类的 MRO 中；类方法存放在元类 MRO 中。
- 类体可以包含表达式/控制流等语句，它们在类定义时执行；但 `var` / `val`
  **在 `oort-object` 中被拒绝**：

  ```oort
  class C {
      var x = 0        # 错误：oort-object 不支持类体变量声明
  }
  ```

  诊断信息应说明替代写法：在 `__init__` 中写 `this.x = ...`。

- 不把类体 `var` / `val` 解释为类属性（Python 的 `Class.attr` 语义），因为那会
  引入共享可变状态并制造与实例字段同名的歧义。
- 如未来确实需要类级共享状态，应使用显式语法（例如 `class var`），届时另立提案；
  在它落地前，共享状态放在模块级变量或显式单例对象中。

### 3. 属性查找与写入

读取 `obj.name`：

1. 实例字段袋；
2. 类 MRO 中的属性/方法（函数绑定为方法）；
3. 元类 MRO 中的类方法；
4. 未找到则抛出 `OortAttributeError`。

写入 `obj.name = value`：

- 如果 `name` 在类 MRO（或类方法所在的元类 MRO）中解析为**可调用的类成员**
  （方法、类方法），拒绝写入并报错：
  `Cannot shadow method 'name' with an instance field`。
- 否则写入实例字段袋。

这条规则保留动态字段的灵活性，同时避免 `this.f = 1` 静默覆盖方法。
未来若引入非可调用的类属性，其与实例字段的优先级需在该提案中另行定义。

### 4. 相等与哈希

- 默认 `==` 为对象身份比较（由 `Object` 的运算符方法提供）。
- 用户可通过 `def operator "=="(other)` 覆盖相等语义（见 OP 0002）。
- 默认哈希为对象身份，因此实例可作为字典键或集合元素。
- 当前没有哈希运算符；覆盖 `==` 不会自动改变哈希。用自定义相等的实例作为
  字典键/集合元素时行为未定义，直到引入显式的哈希协议。

### 5. 字段初始化器（P1，可选，另行提案）

`oort-object` v1 不提供字段初始化器。若后续需要减少 `__init__` 样板，可另立提案，
但必须满足：

- 按“基类 → 子类、类体内文本顺序”对**每个实例**求值，而不是在类定义时求值一次；
- 在 `__init__` 之前执行；
- 不保证初始化期间虚方法调用的行为（建议禁止或在规范中明确为未定义）；
- 语法不与局部 `var` / `val` 混淆（例如显式的 `field` 关键字）；
- 不改变“字段袋开放、方法不可遮蔽”的规则。

### 6. 与 `oort-core` 的边界

| 维度 | `oort-object` | `oort-core` |
|------|---------------|-------------|
| 实例状态 | 开放字段袋 | 固定槽（slot） |
| 类体字段声明 | 拒绝 | 槽声明 + 类型 + 确定赋值 |
| 字段初始化 | 在 `__init__` 中赋值 | 槽初始化器/构造函数，有确定赋值检查 |
| `val` | 不作为字段声明 | 只读槽 |
| 属性查找 | 实例袋优先，禁止遮蔽方法 | 槽/方法优先，规则由静态对象模型定义 |
| 类型标注 | 解析但忽略 | 静态检查 |

两个方言共享 `this.x` 的语法外观，但语义由方言配置决定；跨方言对象通过显式边界
传递，不共享字段布局假设。

## 示例

```oort
class Counter {
    def __init__ {
        this.n = 0
    }

    def increment {
        this.n = this.n + 1
        this
    }
}

val c = Counter()
c.increment()
print(c.n)          # 1
print(c.missing)    # OortAttributeError
```

方法遮蔽被拒绝：

```oort
class C {
    def f: 1
}

val c = C()
c.f = 2             # 错误：不能用一个实例字段遮蔽方法 f
```

## 破坏性变更

- 类体 `var` / `val` 从“静默的类作用域局部变量”变为显式错误。
- `this.method = value` 从“允许遮蔽方法”变为显式错误。
- 现有示例与测试没有依赖这两种行为；项目处于 `0.x`，允许破坏并在
  `CHANGELOG.md` 中记录。

## 替代方案

1. **Python 式类属性**：类体 `var` 求值一次并作为类属性，实例读取回退到类。
   会引入共享可变状态（`var xs = []` 被所有实例共享），且与实例字段同名时语义混乱。
   放弃。
2. **在动态方言中实现槽**：固定布局、getter/setter、`val` 只读需要类型与确定赋值
   分析配合；半实现的槽会阻碍后续 `oort-core` 设计。放弃。
3. **把字段初始化器作为 P0**：能减少样板，但引入初始化顺序、虚调用、继承覆盖等
   问题，不是动态对象模型的核心。推迟到 P1 单独提案。
4. **类 MRO 优先（设计 04 的 Slot-Bag 顺序）**：适合固定槽模型；动态方言采用
   实例袋优先更符合原型/脚本直觉。两方言分别采用各自顺序。

## 正交性检查

- **运算符**：不改变运算符重载；字段访问与运算符方法相互独立。
- **模块/标准库**：对象模型不依赖模块系统；模块级共享状态可作为类体变量的替代。
- **类型系统**：`oort-object` 的类型标注仍被忽略；静态检查属于 `oort-core`。
- **元类**：类方法查找路径不变；本提案只约束实例字段与类成员的关系。
- **DSL**：接收者 lambda、`@DslMarker` 等机制作用于作用域/属性查找，不改变字段袋模型。

## 实现计划

1. 方言契约落地后，在 `oort-object` 的语义分析中拒绝类体 `VarDecl`，并给出
   “在 `__init__` 中赋值”的诊断。
2. 在属性写入路径中加入方法遮蔽检查，覆盖实例方法与类方法。
3. 测试：动态字段增删改、缺失字段错误、类体变量拒绝、方法遮蔽错误、
   默认相等/哈希、`operator "=="` 覆盖。
4. 更新 `docs/spec/05-classes.md`、`docs/spec/06-conformance.md` 与
   `docs/implementation/04-class-system.md`。
5. 字段初始化器与显式类属性各自另立提案。

## 未解决问题

- 方法遮蔽检查是否也覆盖元类上的类方法？建议覆盖，诊断中说明冲突来源。
- 默认哈希与自定义 `==` 的一致性：需要引入 `operator "hash"` 还是禁止自定义相等
  对象作为键？
- 类体中的副作用语句是否保留？当前建议保留，但规范需说明其执行时机。
- 字段初始化器的语法与求值时机（若未来实现）。
