# OP 0001: 特性分层与语言方言

- **状态**：Accepted
- **作者**：Oort 设计讨论
- **相关**：[OP 0002](0002-dsl-support.md)、[OP 0005](0005-type-system.md)、
  [OP 0007](0007-oort-object-object-model.md)、[设计笔记 03](../design/03-type-system-design.md)

## 摘要

把语言特性按“核心基座 / 类型系统 / 抽象机制 / 元编程”分层，并允许同一编译器
通过**模块级方言**（oort-core / oort-object / oort-systems …）提供不同的语义组合。
一个编译单元只能属于一种主方言；不同方言通过统一 HIR 与显式 FFI 边界互操作。

## 动机

C++ 的主要教训不是“某个特性设计得蠢”，而是：

- 所有范式在同一语义空间内无差别融合，互相污染（宏破坏作用域、模板特化破坏泛型一致性）；
- 为兼容/局部优化引入特例（`std::vector<bool>` 破坏容器语义、`iostream` 把格式化状态
  塞进共享流对象）；
- 新需求不断以补丁形式叠加（SFINAE → `void_t` → `if constexpr` → concepts）。

Oort 希望在**一门语言家族**内覆盖多种范式，同时避免这种语义纠缠。

## 设计

### 1. 特性分层

| 层级 | 内容 | 策略 |
|------|------|------|
| L1 核心基座 | 类 C 语法、表达式、一等函数、闭包、容器、内存管理策略 | 先做且稳定 |
| L2 类型系统 | 静态类型、类型推导、泛型、ADT、模式匹配 | 在动态语义稳定后引入 |
| L3 抽象机制 | Trait/Protocol、尾随闭包、自定义运算符、中缀调用 | 作为正交扩展 |
| L4 元编程 | `comptime`、语法宏、过程宏 | 最后做；默认关闭 |
| — 高风险 | 高阶类型（HKT） | 默认砍掉；若做，需单独立案 |

### 2. 方言（Dialects）

| 方言 | 定位 | 关键特性 | 明确排除 |
|------|------|----------|----------|
| `oort-object`（当前） | 动态脚本、DSL、原型 | 元类、动态派发、开放类、闭包 | 静态类型、裸指针 |
| `oort-core` | 静态、函数式核心 | 强类型、HM/双向推导、ADT、模式匹配 | 传统继承、动态派发 |
| `oort-systems` | 系统/底层 | 手动内存、裸指针、`comptime`、C ABI | GC、动态派发 |
| `oort-meta` | 编译期元编程 | AST 操作、过程宏 | 运行时语义 |

DSL 不是独立方言，而是与“类型纪律”正交的维度：

|  | 动态 | 静态 |
|---|---|---|
| **DSL 语法关闭** | `oort-object` | `oort-core` |
| **DSL 语法开启** | `oort-script` | `oort-builder` |

### 3. 模块级方言控制

```oort
#lang oort-object
```

- 每个模块（文件）显式声明一种主方言；编译器加载对应的语义规则与 Pratt 运算符表。
- **禁止**在模块内混用方言；跨方言调用必须经过显式边界。
- 这类似 Rust Editions / Haskell `LANGUAGE` pragmas，但更彻底：语义检查器彼此隔离。

实现（2026-11-18）：`#lang` 在编译入口按**首行预处理**识别，范围仅限第一行
（允许 UTF-8 BOM）。该行对词法器仍是注释，因此不改变行号。非首行声明、未知
方言、已注册但未实现的方言都会得到显式诊断。`DialectConfig` 持有特性开关与
Pratt 表工厂；`ASTBuilder` 与 `Pass1Analyzer` 接收当前方言。

### 4. 统一 HIR 与边界

```
源码 → 共享前端（超集语法 + Pratt）
     → Dialect Router
     → 各方言语义分析器（隔离）
     → 统一 HIR（Low-level）
     → 优化 / 后端
```

- 方言特定语义在进入 HIR 前被“编译掉”。
- 跨方言调用使用显式 `foreign` 声明与边界块，强制处理数据布局、内存所有权与错误模型。
- 跨方言共享的抽象通过 Trait/Protocol 表达：静态方言静态分派，动态方言动态分派。

### 5. 开发模型：共享骨架 + 方言垂直切片（2026-11-18 已接受）

方言不仅是运行时的开关，也是**开发与验收的主轴**。但为了避免重复实现，
需要把“共享骨架”和“方言语义”分开：

| 层 | 内容 | 纪律 |
|----|------|------|
| **共享骨架** | 词法/语法超集、AST、源码位置、诊断、模块加载、CLI/REPL、测试框架 | 不承载方言策略；不为单个方言加特判 |
| **方言切片** | 各方言的对象模型、语义分析、特性门控、规范与测试 | 一个方言一个语义分析器；方言内规则一致 |
| **共享执行/后端** | 树遍历解释器 → 统一 HIR → 字节码 VM | 不按方言复制；方言差异在进入 HIR 前消化 |

开发规则：

1. **一次只做一个方言的端到端闭环**，但共享骨架保持方言无关。
2. **一份语法超集**：方言特定语法在语义分析阶段门控，不提前分叉 ANTLR 文法；
   只有当分叉成本明确低于共享成本时才拆文法。
3. **按需抽象**：共享组件在第一个方言需要时实现，在第二个方言复用时才一般化。
   不为想象中的方言提前造 HIR、运行时抽象或插件框架。
4. **方言 v1 的完成定义**：规范声明的特性全部可端到端运行，并有正向测试、
   拒绝测试、示例与文档；不以“所有后端/优化完成”为标准。
5. **解释优先，后端共享**：两个方言都先用树遍历解释器跑通 v1；字节码/LLVM
   在对象模型稳定后作为共享后端实现，禁止“每方言一套后端”。
6. **第二个方言尽早探针**：在第一个方言深度打磨前，用一个很薄的
   `oort-core` 子集验证方言路由与语义隔离，避免共享层泄漏。

推进顺序：

1. 方言契约（`#lang`、`DialectConfig`、门控、测试/示例目录）。
2. `oort-object` v1：动态对象模型、参数绑定、模块/标准库/迭代器协议。
3. `oort-core` 探针，然后完整类型系统、ADT/模式匹配、静态对象模型与槽。
4. 两个 v1 之后：统一 HIR、共享字节码 VM、与解释器对拍。
5. `oort-systems` / `oort-meta` 最后；DSL 是正交开关，不单独建管线。

对象模型的归属也因此明确：

- `oort-object` 使用**开放字段袋**，不引入槽（见
  [OP 0007](0007-oort-object-object-model.md)）；
- 槽（固定布局、确定赋值、`val` 只读、getter/setter）属于 `oort-core`
  的静态对象模型，与类型系统一起设计；
- 因此“类槽变量”不是 `oort-object` 的 P0。

## 正交性检查

- 与类型系统：方言决定类型检查强度，但**同一方言内**规则一致。
- 与类/函数：`oort-object` 的类与 `oort-core` 的结构体不共享继承语义。
- 与元编程：元编程作为一个方言/编译期阶段，不污染运行时语义。
- 不引入特例：方言是“整模块开关”，而不是逐表达式开关。
- 与开发流程：共享骨架不感知方言；方言差异只存在于语义分析与规范中。

## 替代方案

1. **单一语言 + 特性开关**：开关组合爆炸，语义纠缠仍在，放弃。
2. **完全独立的多门语言**：无法共享前端、库与互操作，放弃。
3. **仅用宏模拟方言**：宏无法改变类型检查与内存模型，放弃。

## 向后兼容

- 当前实现等价于 `oort-object`；引入方言是增量变化。
- 缺省方言为 `oort-object`，允许显式 `#lang oort-object`；其他方言必须显式声明。
- 项目处于 `0.x`，允许为划清方言边界而破坏现有行为（例如拒绝类体
  `var`/`val`，见 [OP 0007](0007-oort-object-object-model.md)），但必须在
  `CHANGELOG.md` 与规范中记录。
