# OP 0005: 类型系统、泛型、ADT 与模式匹配

- **状态**：Draft
- **作者**：Oort 设计讨论
- **相关**：[OP 0001](0001-feature-layers-and-dialects.md)、[设计笔记 03](../design/03-type-system-design.md)、[设计笔记 01](../design/01-runtime-value-representation.md)

## 摘要

为 Oort 引入**模块级渐进类型**：动态模块保持现有解释执行；静态模块获得类型检查、
泛型、ADT、模式匹配与 `Result`/`Option` 错误处理。首批只做双向类型检查与局部推导，
不做 HKT，不做全程序 HM。

## 动机

- 当前类型标注被解析但完全忽略，容易让用户误以为有检查。
- 现代语言的经验（Rust/Swift/TypeScript）表明：ADT + 模式匹配比传统继承更适合
  数据建模；`Result`/`Option` 比异常更适合显式错误处理。
- C++ 的教训：`std::vector<bool>` 说明“为优化引入语义特例”代价极高；类型
  萃取/偏特化说明开放的编译期类型计算会失控。Oort 应从一开始就限定类型级编程的边界。

## 设计

### 1. 渐进类型边界

- 以**模块**为单位选择动态/静态（与 [OP 0001](0001-feature-layers-and-dialects.md) 的方言一致）。
- 静态模块内所有函数签名与变量必须有类型；动态边界处用 `any` / 运行时检查。
- 边界 trampoline：动态调用静态、静态调用动态时插入装箱/检查代码。
- 类型错误带 blame（错误归责到具体边界），不把错误推给调用者。

### 2. 检查算法

- 基础：双向类型检查（`check(expr, expected)` / `infer(expr)`）。
- 局部推断：`val x = 42` 推断为 `Int`；函数返回类型可由函数体推断。
- 泛型：显式类型参数 `[T]`，调用处做统一（unification）；可选的全程序 HM 作为后续扩展。
- 不做高阶类型（`F[_]`）：实现成本高、对多数用户价值低；若需要，单独立案。

### 3. 泛型实现策略

- 内部单态化（monomorphization）：适合静态模块与 LLVM 后端；
- 边界处类型擦除：动态与静态互操作时使用；
- 混合策略，具体边界见 [设计笔记 03](../design/03-type-system-design.md)。

### 4. ADT 与模式匹配

```oort
enum Option[T] {
    Some(value: T)
    None
}

match opt {
    Some(v) => v,
    None => 0,
}
```

- 标签联合（tagged union），编译期穷尽性检查；
- 模式：字面量、变量、构造器、元组/列表、通配符、守卫；
- 编译为决策树，而不是线性 `if` 链；
- 与现有 `class` 并存：ADT 用于数据，类用于行为/动态派发。

### 5. 错误处理

- 标准库提供 `Result[T, E]` 与 `Option[T]`，配合模式匹配。
- 不使用 `try/catch` 作为主要控制流；异常仅用于不可恢复错误（或完全不引入）。
- `?` 传播语法作为糖，最终降级为 `match`。

### 6. 内存管理

- 动态方言：Tracing GC（简单、可移动）或 ARC（无暂停但循环引用需处理）。
  首选简单 Mark-Sweep，后续可替换。
- 静态方言：所有权/生命周期或区域分配（远期）。
- 该决定影响闭包表示与 FFI，需在字节码/LLVM 实现前确定。

### 7. 运算符重载（类型系统的一部分）

- 不采用 C++ 的全局符号重载与偏特化；采用 trait 风格：
  `Add` 等接口按类型实现；
- 对称运算（`a + b` 与 `b + a`）通过自由函数或交换律声明处理，避免 `__radd__` 式隐式规则；
- 运算符声明语法见 [OP 0002](0002-dsl-support.md)。

## 正交性检查

- 与类：ADT 不参与继承；类不要求 ADT 语义。
- 与宏：类型检查在宏展开之后、运行之前。
- 与字节码：类型信息用于优化，但动态模块不依赖它。

## 替代方案

1. **全程序 HM**：推断强，但错误信息与模块化编译困难，且与类/子类型交互复杂。
2. **纯动态 + 运行时检查**：简单，但无法提供编译期保证。
3. **类型类 + 开放世界**：表达力强，但实例解析复杂度高（Scala/Haskell 的教训）。

## 实现计划

1. 拒绝清单先行：在静态方言中，未实现特性仍显式报错。
2. 双向检查 + 局部推断 + 基础泛型。
3. ADT + `match` + 穷尽性检查。
4. `Result`/`Option` 与标准库。
5. 边界 trampoline 与 blame。
6. 类型级 `comptime`（最后，需与宏提案统一）。

## 未解决问题

- 子类型与泛型变型（`List[Dog]` 是否是 `List[Animal]`）。
- 动态方言中的类型标注是“文档”还是“运行时断言”？
