# 并发与 ABI 设计

> 整合来源：`chat-字节码虚拟机设计与多线程支持`, `chat-系统级编程语言ABI设计考量`

---

## 1. 并发模型

### 1.1 核心决策

**无 GIL**：支持真正的多核并行。

| 特性 | 选择 | 理由 |
|------|------|------|
| 线程模型 | M:N 绿色线程 | 轻量、可调度 |
| 调度策略 | 安全点抢占 | 避免协作式调度的问题 |
| 内存模型 | Per-thread heap + shared heap | move semantics 数据传输 |
| 通信方式 | CSP 通道 (主要) + mutex (回退) | 安全 + 灵活 |

### 1.2 静态模块并发注解

```oort
@thread_safe        # 可安全跨线程调用
@blocking           # 会阻塞，应在独立线程运行
@single_thread      # 仅限单线程使用
@no_gc_point        # 无 GC 安全点（性能关键路径）
```

### 1.3 VM 感知的 ABI

为并发代码自动生成 trampoline，处理：
- GC 安全点注入
- 线程本地存储访问
- 栈溢出检查

### 1.4 与现有方案的对比

| 语言 | 模型 | 优点 | 缺点 |
|------|------|------|------|
| Python | GIL | 简单 | 无法并行 |
| Go | Goroutine + channel | 简单高效 | GC 压力 |
| Rust | OS thread + async | 零成本 | 学习曲线 |
| Erlang | Actor | 隔离性好 | 消息复制开销 |
| **Oort** | M:N + CSP | 兼顾 | 实现复杂 |

## 2. ABI 设计

### 2.1 核心决策

**无稳定 ABI**，但提供高质量 C FFI。

理由：
- 语言仍在演进，稳定 ABI 会限制设计空间
- C FFI 可以接入几乎所有生态系统
- 参考 Zig 和 Swift 的教训

### 2.2 三阶段路线

| 阶段 | 目标 | 说明 |
|------|------|------|
| Phase 1 | C ABI FFI | `extern "C"` 互操作 |
| Phase 2 | 最小稳定子集 | 核心类型的稳定表示 |
| Phase 3 | 可选原生 ABI | 如果语言成熟 |

### 2.3 FFI 安全规则

1. **永远不在 ABI 边界抛异常**
2. 明确的所有权语义（谁分配、谁释放）
3. 错误码返回而非异常传播
4. 跨语言字符串使用 `*const u8` + length

### 2.4 各语言 ABI 策略对比

| 语言 | ABI 策略 | 教训 |
|------|---------|------|
| C | 稳定 ABI | 简单但表达力有限 |
| C++ | 不稳定 ABI | 名字修饰导致链接问题 |
| Rust | 不稳定 ABI | `extern "C"` 用于 FFI |
| Zig | 可选稳定 | 通过 `extern` struct |
| Swift | 不稳定 ABI | 二进制兼容性差 |
| Go | 稳定 ABI (cgo) | 性能开销大 |

## 3. 注意事项

- 并发和多线程是远期目标，当前优先级低
- C FFI 的实现依赖 LLVM 后端或 Rust 实现
- Python 原型阶段不考虑并发
